# Vocabulary Audit Policy

この文書は、英単語検定1級対策用データと `vocab-app-study` の監査・修正基準を固定するための規範です。目的は辞書データベースの網羅性ではなく、学習価値、四択問題の一意性、データ整合性、再現可能な保守を最大化することです。

## 1. 基本原則

- 1単語1行を維持する。辞書的な全sense分離は行わない。
- `meaning` には、試験学習上重要な現代主要義・重要副義だけを保持する。稀義・古義・専門枝義は、学習価値が明確な場合だけ採用する。
- 辞書上存在するだけの別品詞は追加しない。`partOfSpeech` は現在の `meaning` に実際に採用されている語義の品詞だけを表す。
- 複数品詞はカンマ区切りで保持する。日本語訳の表面形だけで品詞を推定・追加しない。
- 不明・競合・根拠不足の場合は元データを維持する。辞書間で扱いが割れる場合も自動統一しない。

## 2. semanticCategory

`semanticCategory` は辞書的な意味分類そのものではなく、四択問題の distractor（誤答選択肢）生成を主目的とする。

- 分類体系の美しさより、実際の四択品質を優先する。
- 近義語が同カテゴリに存在すること自体は問題としない。
- カテゴリ変更は、実際に悪問・候補不足・不自然な選択肢が再現できた場合を主要根拠とする。
- 個別近義語ペアをゼロにするための過剰な統合・再分類はしない。

## 3. 四択候補の安全性

候補は次の順序で扱う。

1. 正答自身を除外する。
2. 同一表示選択肢を除外する。
3. 正答と日本語訳断片が重なる語を除外する。
4. `distractorExclusions.js` の監査済み個別除外群を除外する。
5. `partOfSpeech` と `semanticCategory` による優先順位を適用する。
6. 同じ優先順位では同Volを優先する。
7. 英→日では、同じ安全性・metadata・Volの範囲内だけ、訳の表示形状が近い候補を優先する。

表示形状による優先は安全性判定より下位とし、同義語除外やmetadata優先を弱めてはならない。

## 4. 個別 distractor 除外

個別除外は「意味が近い」だけでは登録しない。

登録条件は、現在の `meaning` を選ばせる問題において、双方を正答と合理的に解釈できる十分な根拠があることとする。主要辞書の定義・synonym関係・包含関係を確認し、対象は stable `wordId` で管理する。

反義語、上位下位語、関連語、ニュアンス差を識別できる近義語は、良い distractor になり得るため原則維持する。

## 5. Hard invariant と heuristic warning

### Hard invariant

違反した場合はデータまたはコードの欠陥として扱う。

- 必須値欠落
- `id` 重複
- `word` 重複
- 許容外 `partOfSpeech`
- `vol1`〜`vol4` 以外の `sourceVol`
- 英→日または日→英で3つの安全な誤答を確保できない
- 無条件 priority 3 に依存しないと四択が成立しない

### Heuristic warning

自動修正・CI失敗の根拠にはしない。

- `meaning ↔ partOfSpeech` の疑義
- 表示形状の偏り
- 意味類似度の高い候補
- 四択の難易度・自然さに関する品質警告

ヒューリスティックは候補抽出器であり、正解判定器ではない。警告ゼロを目的にデータを変更しない。

## 6. meaning の表記

意味内容を変えない表記正規化は、コーパス全体の一貫性を高める場合に限り行う。

- 目的語などのプレースホルダーは `～` を使用する。
- 算用数字は原則半角を使用する。
- 表記一致だけを理由に意味情報・品詞・カテゴリを変更しない。

## 7. 語源情報

- 語源は空欄を埋めること自体を目的としない。
- 歴史的形成と、学習者向けの後付け形態素分解を混同しない。
- `morpheme` と `morphemeMeaning` は対応を維持する。
- `semanticDevelopment` は、語源から現代語義への意味変化を学習可能な形で説明する。
- 根拠不足の場合は推測で補完しない。

## 8. 発音

`phonetic`、`pronunciationSource`、`pronunciationStatus` は監査済み情報を優先する。`verified` 行は監査済みデータを正本とし、外部API/TTSは表示・再生のフォールバックとして扱う。

## 9. データ契約

Sheets → Apps Script → Firestore → `data.js` → UI の経路で、次の学習列を保持する。

- `id`
- `word`
- `meaning`
- `morpheme`
- `morphemeMeaning`
- `semanticDevelopment`
- `partOfSpeech`
- `semanticCategory`
- `phonetic`
- `pronunciationAudioUrl`
- `pronunciationSource`
- `pronunciationStatus`

`level` は同期時に `vol1`〜`vol4` へ分割するために使い、アプリ内部では `sourceVol` として復元する。

## 10. テストと監査の責務分離

- GitHub Actions: コードと監査ロジックの回帰テストを `npm test` で実行する。
- `npm run audit:vocab -- <csv>`: 実データの hard invariant を検証する。
- `npm run audit:quality -- <csv>`: 実データの四択品質を advisory として評価する。

私有の5,758語CSVをCIのためだけにGitHubへ複製しない。監査ロジックはCIで検証し、私有実データは明示的なデータ監査で検証する。

## 11. 変更ルール

- 修正は根拠が十分な場合だけ行う。
- 監査で発見した問題は、可能なら原因レイヤー（データ、category、除外、生成ロジック、同期）を特定して最小限に修正する。
- 同じ問題が再発し得る場合は回帰テストを追加する。
- 大規模構造変更は、現行の単検専用用途で明確な利益がある場合だけ採用する。
- 変更内容と監査結果はスプレッドシートの変更履歴・監査シートに記録する。
